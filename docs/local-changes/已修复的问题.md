# 控制台问题记录与修复（main 分支）

> 时间：2026-09-14
> 环境：http://localhost:18080（main 分支新版控制台）

## 问题 1：`/api/v1/agents/<id>/definition` 返回 404

**现象**：控制台报 `Failed to load resource: 404`，路径形如
`/api/v1/agents/…33ab5c/definition`。

**原因**：库里有一个**创建时没带 definition 的半成品 Agent**（`agentKey=deepseek-agent`，
id `fec26c3c-c250-4253-a63f-a7d19933ab5c`），状态一直停在 `provisioning`。
前端 `getAgent()` 会并行请求目录与 definition，这条记录没有 definition 就返回 404。
（这个记录是调试过程中用 API 只传 `agentKey/name/model` 创建的，不是控制台正常流程产生的。）

**修复**：用控制面的「初始化 definition」接口补上：

```bash
curl -X POST "http://localhost:18080/api/v1/agents/<id>/definition" \
  -H "Authorization: Bearer $TOKEN"
# 再 PATCH 补 name/model（version 必填）
curl -X PATCH "http://localhost:18080/api/v1/agents/<id>/definition" \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"name":"DeepSeek 助手","model":"deepseek:deepseek-chat","system":"你是助手。","maxIters":10,"version":1}'
```

修复后三个 Agent 的 definition 全部返回 200。

**根因提醒**：用 API 创建「托管」Agent 必须同时给 `definition`，否则会 500
`managed Agent requires definition`，并留下无 definition 的记录。控制台表单会自动带上。

## 问题 2：`Create & open agent` 按钮一直灰色

**现象**：在 `/agent-center/agents/new` 填了名称，按钮仍然不可点。

**原因**：这是**前端真实 bug**。按钮的可用条件
（`frontend/src/pages/AgentCreatePage.tsx:298`）是：

```js
const canSubmit = !submitting && !!name.trim() && !!agentKey.trim() && !!execution;
```

而 `agentKey` 是从名称自动生成的 slug：

```js
e.target.value.trim().toLowerCase().replace(/[^a-z0-9_-]+/g, '-').replace(/^-+|-+$/g, '')
```

正则把所有非 ASCII 字符替换成 `-`，再把首尾 `-` 去掉。因此**纯中文名称会得到空字符串**，
`agentKey` 为空 → 按钮永远置灰。实测：

```text
输入 '客服助手'        -> agentKey ''                按钮可点=False
输入 '报表助手'        -> agentKey ''                按钮可点=False
输入 'DeepSeek 助手'  -> agentKey 'deepseek'        按钮可点=True
输入 'Repository reviewer' -> 'repository-reviewer'  按钮可点=True
```

**修复**：给 `AgentCreatePage.tsx` 加稳定兜底 key，并在 agentKey 输入框也去掉首尾连字符：

```ts
// 模块级：每次页面加载固定
const AGENT_KEY_FALLBACK = `agent-${Math.random().toString(36).slice(2, 8)}`;

// Name onChange
const slug = e.target.value.trim().toLowerCase()
    .replace(/[^a-z0-9_-]+/g, '-').replace(/^-+|-+$/g, '');
setAgentKey(slug || (e.target.value.trim() ? AGENT_KEY_FALLBACK : ''));
```

改完执行 `cd frontend && npm run build`（产物输出到 `aistio/ui/`，aistiod 直接静态服务，无需重启后端）。
修复后实测：中文名 → `agent-3fao5f`，创建返回 201、状态 `active`。

> **临时绕过（不重新构建也能用）**：在表单里手动填写 **Agent Key** 字段（例如 `my-agent`），
> 按钮就会变为可点。

## 附带调整：重启不再清空数据

官方 `dev-up.sh` 默认 `BUILDER_RESET_DB=1`，每次启动会 DROP 掉 `cp/rt/dp` 三个 schema，
你创建的 Agent 会全部消失。已在 `scripts/start.sh` 里把默认值改为 `0`（保留数据）：

```bash
./scripts/start.sh                  # 保留数据
BUILDER_RESET_DB=1 ./scripts/start.sh   # 需要清空重建时
```

## 问题 3：Team 模式下 DeepSeek 400 `Invalid 'tools[N].function.name'`

**现象**：团队任务执行报错
`Invalid 'tools[N].function.name': string does not match pattern '^[a-zA-Z0-9_-]+$'`，
任务状态 failed，错误代码 turn_failed。

**原因**：Team/Issue 协作模式会给 Agent 注入 `aistio-collaboration` MCP 服务器，
其工具名带**点号**（`issue.get`、`run.graph`、`issue.acceptance.update`、`task.begin_work` 等 25 个）。
DeepSeek（OpenAI 兼容）要求函数名只含 `[a-zA-Z0-9_-]`，点号直接 400。

**修复**：把协作工具名统一改为下划线（`issue_get`、`run_graph`、`issue_acceptance_update`、
`task_begin_work` …），同步修改 aistio 的定义/分发/提示词、dataplane 提示词、
extensions-aistio 协作客户端和 dsh SDK，共 40+ 个文件。重新编译 aistiod 与 dataplane。

**过程中踩的坑**：

1. 盲替换 `issue.accept` → `issue_accept` 会先把 `issue.acceptance.update` 污染成
   `issue_acceptance.update`，导致整名替换失效——第二次扫描才抓到。
2. Java 里 `task.get("key")` 这类 **Map 取值**会被误伤成 `task_get("key")`，编译报错，
   需精确只替换字符串字面量，并手工还原 2 处。
3. 重启时直接用 `dev-up-local.sh` 会丢掉 `DEEPSEEK_API_KEY`（key 靠 `start.sh` 从
   `~/.deepseek-key` 注入），导致错误一度变成 "DEEPSEEK_API_KEY is required"。

**验证**（端到端）：

```text
创建 Team（leader=DeepSeek 助手）→ 创建 Issue 指派给团队
→ AgentTask queued → running → completed
工具注册名：issue_acceptance_update / run_node_complete / math_evaluate（全部下划线）
DeepSeek 调用：400 次数 0
Issue 状态：in_review
Agent 真实回复：「我收到的任务是『协作工具修复验证』……按指令未调用任何工具。」
```
